# FreeDOM、静态子图与 BTC 接入方案

日期：2026-09-16。状态：方案阶段；尚未移植、编译或运行 FreeDOM。

## 1. 目标与模块职责

目标是减少移动物体在重定位地图中的残影，并在保留环境结构的静态子图上建立 BTC 描述子库。

| 模块 | 负责的工作 | 交付给后续模块的内容 |
| --- | --- | --- |
| Odin 里程计与点云 | 提供观测和运动估计 | 带时间戳的点云、位姿及传感器外参 |
| FreeDOM | 根据连续观测维护自由空间与静态地图，清除动态物体影响 | 随观测更新的静态地图 |
| 子图构建 | 按轨迹选取局部区域，保留相邻区域的重叠并适度降采样 | 子图点云、编号、局部坐标系及全局位姿 |
| BTC | 提取与检索环境几何描述子 | 候选子图及用于几何验证的对应关系 |
| 重定位配准 | 验证候选并求解位姿 | 当前传感器/机器人的地图位姿 |

FreeDOM 的官方定位是静态地图构建中的动态物体去除。它不能替代里程计、BTC 或实时避障。静态地图质量是否改善、BTC 是否更稳定，需要在 Odin 数据上验证。[官方仓库](https://github.com/LC-Robotics/FreeDOM)

本次源码核对基于上游提交 [`dcfd5690cafddf121a80bd8ea477807d9656748e`](https://github.com/LC-Robotics/FreeDOM/commit/dcfd5690cafddf121a80bd8ea477807d9656748e)。下述原接口是上游事实，实施步骤与新路径是本项目建议。

## 2. 推荐的数据流与实施顺序

### 建图分支

1. 接收逐帧点云、对应时刻的传感器位姿和外参。
2. 校验时间与坐标关系，做必要的无效点过滤。
3. 交给 FreeDOM，持续更新静态地图。
4. 首版在一轮建图完成、静态地图保存后，结合保存的轨迹切出有重叠的局部子图。
5. 对子图适度降采样，提取 BTC，保存地图与描述子库。

上游 `static_pointcloud` 发布的是当前静态地图的可视化点云，并非本帧新增的静态点。地图清理会利用后续证据修改旧数据，因此不能逐次把该话题追加到另一个地图里，否则会重复累计并保留已经失效的动态点。首版优先使用保存接口输出的 `static_map_point.pcd`，而不是把可视化发布当作完整地图存储协议。[发布实现](https://github.com/LC-Robotics/FreeDOM/blob/dcfd5690cafddf121a80bd8ea477807d9656748e/src/visualization.cpp)、[地图修订](https://github.com/LC-Robotics/FreeDOM/blob/dcfd5690cafddf121a80bd8ea477807d9656748e/src/mrmap.cpp)、[保存实现](https://github.com/LC-Robotics/FreeDOM/blob/dcfd5690cafddf121a80bd8ea477807d9656748e/src/freedom.cpp)

这里的“先保存再切子图”是本项目的首版设计建议，目的是让子图和描述子对应同一份清理结果。在线建图算法不要求所有下游步骤都必须在线运行。

后续如需边建图边提取 BTC，应在地图内容稳定后生成子图；如果后续清理改变了已经入库的子图，必须同步更新点云与描述子，不能只更新其中一个。稳定判据和更新时间应通过回放确定，暂不指定固定等待秒数。

### 实时感知与避障分支

继续使用当前观测维护附近障碍物。行人等动态目标虽然不应长期留在重定位地图中，但仍需出现在实时障碍物观测里。FreeDOM 清理后的静态地图不能成为唯一避障输入。

现有 `/cloud/obstacles` 只是当前平面分割后的非地面点，不等于动态物体检测、目标跟踪或完整避障。

### 重定位分支

当前连续观测形成局部查询点云，采用与建图库一致的特征提取设置，通过 BTC 检索、几何验证和精配准定位。首版不把“先完成一轮 FreeDOM 动态判定”设成每次重定位的硬性前置条件；查询侧是否使用动态清理结果，需要比较延迟、点数和重定位成功率。[BTC 官方实现](https://github.com/hku-mars/btc_descriptor)

## 3. 当前工程的接入条件

以下是本地代码事实，以及由这些事实导出的设计要求。

### ROS 版本

- 当前点云节点使用 ROS 2 的 `ament_cmake`、`rclcpp`，见 [CMakeLists.txt](../src/planner/CMakeLists.txt)。
- FreeDOM 官方使用 `catkin build` 和 `roslaunch`，是 ROS 1 工程，不能直接放进当前 ROS 2 工作空间后作为 ROS 2 节点运行。[官方构建说明](https://github.com/LC-Robotics/FreeDOM#1-build)
- 建议新增独立的 ROS 2 FreeDOM 包，保留算法实现，移植 ROS 接口、参数、消息订阅发布、启动与保存入口。固定上游提交并保留来源及许可证。首版不把 ROS 1/ROS 2 桥作为长期运行依赖。

### 上游输入输出接口

| 接口 | 已核实行为 | ROS 2 接入要求 |
| --- | --- | --- |
| 点云输入 | `sensor_msgs/PointCloud2` 转成 `pcl::PointXYZ` | 核对坐标含义；不依赖 RGB 或强度；逐点时间不会由 FreeDOM 自动处理 |
| 位姿输入 | 按点云时间戳查询 `map_tf_frame -> sensor_tf_frame` 的 TF，上游不直接订阅里程计 | 优先复用当前 `odom -> imu -> lidar` TF 链及 ROS 2 tf2 缓存 |
| 静态点云发布 | `static_pointcloud`，当前静态地图的可视化输出 | 用于观察当前地图，不作为逐帧新增点接口 |
| 保存入口 | `/save_map`，保存 `static_map_voxel.pcd` 与 `static_map_point.pcd` | 移植保存入口，确保保存结果与轨迹、坐标系、参数一同记录 |

接口依据：[freenode.cpp](https://github.com/LC-Robotics/FreeDOM/blob/dcfd5690cafddf121a80bd8ea477807d9656748e/src/freenode.cpp)、[启动参数](https://github.com/LC-Robotics/FreeDOM/blob/dcfd5690cafddf121a80bd8ea477807d9656748e/launch/run_freedom.launch)、[freedom.cpp](https://github.com/LC-Robotics/FreeDOM/blob/dcfd5690cafddf121a80bd8ea477807d9656748e/src/freedom.cpp)。

### 坐标系与传感器原点

- `/odin1/cloud_slam` 的点已经在 `odom` 坐标系中，驱动发布代码见 [host_sdk_sample.h](../src/odin_ros_driver/include/host_sdk_sample.h)，函数 `publishPC2XYZRGBA`。
- `/odin1/odometry` 描述的是 `imu` 在 `odom` 中的位姿，见同文件的 `publishOdometry`。
- 驱动还维护 `imu -> lidar` 外参。FreeDOM 的自由空间判断需要正确的观测起点，不能直接把 IMU 的平移当成雷达原点。

统一记号：`T_A_B` 把 B 系坐标变换到 A 系。应计算：

`T_odom_lidar = T_odom_imu × T_imu_lidar`

如果 FreeDOM 接口要求雷达局部点云，则使用：

`p_lidar = inverse(T_odom_lidar) × p_odom`

如果移植后的接口直接接受 `odom` 系点，则明确同时传入雷达原点/位姿，避免再次对已经配准的点做同一个变换。

`cloud_slam` 能否用于自由空间估计，还要通过数据确认：它必须保留适合逐帧观测分析的可见表面，不能把已经混合多个时刻的地图快照当作一帧测量。若不满足，评估使用 `cloud_raw`、逐点时间信息和必要的运动补偿；不能直接切换话题就认为接入完成。

### 时间同步

当前节点分别处理点云与里程计，没有为点云查找同一采样时刻的完整雷达位姿，见 [main.cpp](../src/planner/src/main.cpp)。

当前驱动配置为 `use_host_ros_time: 1`，即按主机接收时刻盖时间戳，见 [control_command.yaml](../src/odin_ros_driver/config/control_command.yaml)。接收时刻接近并不能证明采样时刻相同。

接入前应比较点云与位姿的采样时间关系，选择能保留该关系的时间方案；优先复用 ROS 2 tf2 的缓存与时间插值，获取点云时刻的完整雷达位姿，避免重复实现里程计同步器。没有有效时间覆盖时，应报告并跳过该帧地图更新，不拿最新一条位姿无条件替代。建图、回放、TF 需使用一致时间基准。

### 滤波顺序与距离裁剪

当前 `CloudPreprocessor` 顺序为无效点/距离过滤、SOR、3 cm 体素降采样，见 [cloud.cpp](../src/planner/src/cloud.cpp)。

其距离计算为 `x² + y² + z²`。输入为 `odom` 系时，这是到 `odom` 原点的距离，不能当作到移动传感器的量程过滤。FreeDOM 输入端应在雷达系裁剪，或计算 `p_odom - sensor_origin_odom` 的距离。

建议 FreeDOM 从原始观测话题接入并自行做必要的有效性过滤，避免直接沿用 `/cloud/downsampled` 作为默认输入。SOR、降采样和测距截断会改变自由空间判断所依据的观测，应逐项验证。用于传感器量程、FreeDOM 状态体素、子图降采样和 BTC 特征提取的参数，分别命名、分别调节，不能共用一个 `voxel_size`。

Odin 的量程、视场和点分布也应单独配置并验证，不能直接照搬 Velodyne 等传感器参数。FreeDOM 将输入转成 `PointXYZ`，不会自动使用 Odin `cloud_raw` 的 `offset_time`；如需运动补偿，应在进入 FreeDOM 前完成。

## 4. 需要新增或调整的部分

下面的新增路径是实施建议，当前只创建本方案文档。

| 路径/模块 | 计划改动 | 所属阶段 |
| --- | --- | --- |
| `src/freedom_ros2/` | 新增 FreeDOM ROS 2 包、上游算法来源记录、节点、配置及启动文件；适配输入、坐标、同步、静态地图发布和保存 | 第一阶段 |
| `src/odin_ros_driver/config/control_command.yaml` | 在采样时间验证后决定时间模式；核对点云、里程计和外参输出开关 | 第一阶段，按验证结果调整 |
| `src/planner/src/cloud.cpp` 及对应头文件 | 若复用量程过滤，修正传感器原点语义并增加回归验证；FreeDOM 独立接入时不强制重构现有预处理器 | 按需 |
| `src/planner/src/main.cpp` | 保留当前观测分支；必要时把输入话题参数化用于实验，避免全局改成静态地图输入 | 按需 |
| 后续子图构建模块 | 从清理后的地图和轨迹生成重叠子图，保存编号、局部点云、位姿与参数 | 第二阶段 |
| 后续 BTC/重定位模块 | 建库、加载、候选检索、几何验证、精配准；与子图编号和版本保持对应 | 第三阶段 |
| `README.md` | 增加各阶段启动、回放、保存和重定位说明，明确实时障碍物与静态地图的用途 | 随功能完成 |

当前 `src/planner` 还没有子图管理或 BTC 接入实现，因此后两阶段属于新增能力。Odin 设备内部保存的地图与主机侧 FreeDOM 静态地图是两套输出；外部清理不会自动改写设备内部地图。

## 5. 验证与阶段完成条件

### 第一阶段：FreeDOM 在 Odin 数据上成立

先记录包含点云、里程计、TF/外参的 rosbag，使用同一段数据对比普通累积和 FreeDOM 输出。

- **静态场景、设备移动**：墙壁和地面应保持一致，检查错误清除是否来自坐标、时间或量程处理。
- **行人穿过后离开**：测量静态地图残影及其清除延迟；同时检查原始实时障碍物分支仍保留人。
- **物体暂时停留、遮挡后重新露出**：观察多帧判定，不能用单帧结果声称完成动态去除。
- **设备转弯、远离起点**：验证有限视场、配准误差和距离裁剪不会把未观测区域误当作自由空间，或把有效点全部裁掉。
- **资源与确定性**：记录输入频率、每次更新耗时、队列延迟、内存、丢帧和保存再加载结果。性能门槛在取得实际输入频率与目标硬件数据后确定。
- **移植验证**：对同一固定输入比较上游与 ROS 2 实现的核心地图结果；再做 ROS 2 输入、TF、保存入口的集成验证。

第一阶段的完成条件是能够稳定回放、保存静态地图，并提供静态结构保留、动态残影和延迟的对比证据。当前未发现可直接用于验证的仓库内 rosbag，效果和速度均未测试。

### 第二阶段：子图可重复生成

子图使用明确局部坐标系，重叠区域几何一致；重载后能通过保存的位姿恢复到地图中；相同地图和参数能生成一致的子图。子图降采样参数通过细节保留和计算量比较确定。

### 第三阶段：BTC 与重定位效果成立

使用不同时刻的查询数据，对比清理前后建库的检索成功率、误匹配、最终位姿误差和耗时。先固定 BTC 参数比较地图处理的影响，再单独调参。环境重复或动态去除造成特征减少时，也应记录退化，不能预先承诺 FreeDOM 一定提高重定位成功率。

## 6. 首版决策摘要

先完成“逐帧观测与雷达位姿 → FreeDOM 静态地图 → 保存与回放验证”，再实现子图与 BTC。静态地图和实时障碍物观测分别服务建图重定位与当前环境感知。当前阶段交付本方案，不修改运行代码或驱动参数。
